# Launcher plugins with code (schema 2)

A schema 2 plugin is a WebAssembly component. The launcher runs it in a sandbox and draws
the page it describes with the launcher's own widgets. The first-party plugins are schema 2:
Event lobbies, Controllers, Game server and Server host. Their sources are in `plugins/`.

Schema 1 plugins (a page described in `plugin.json`, [pages.md](pages.md)) keep working.
Launchers before 0.12.4 refuse schema 2 and keep reading the v1 catalogue `plugins.json`.
Newer launchers read the signed `plugins.v2.json` first.

## plugin.json

```json
{
  "schema": 2,
  "id": "event-lobbies",
  "name": "Event lobbies",
  "version": "0.2.0",
  "author": "heisthecat31",
  "summary": "…",
  "icon": "calendar",
  "wasm": "plugin.wasm",
  "permissions": {"net": ["relay", "typed"], "relay_password": true, "play": true},
  "settings": { "store": {"file": "settings.json", "format": "json"}, "sections": [ … ] }
}
```

- **`wasm`** names the component in the plugin's folder.
- **`settings`** works exactly as in schema 1 ([settings.md](settings.md)), presets
  included. The launcher keeps the values. The page shows a section with a `form` node and
  the presets with a `presets` node.
- **`data`, `actions` and `page`** are schema 1 only. The launcher ignores them here and
  warns about them.

## What a plugin may do

The player allows a plugin's permissions when getting it, and again when an update asks for
more. The launcher refuses any call outside them.

| `permissions` | What it allows |
| --- | --- |
| `net: ["https://host:port", …]` | Requests to those servers. |
| `net: ["relay"]` | Requests to the classic lobbies server the launcher's settings name. |
| `net: ["typed"]` | Requests to servers the player typed in the plugin's settings. |
| `relay_password` | The launcher fills the player's classic lobbies name and password into a request body's `"{relay.name}"` and `"{relay.password}"`. It does this for the classic lobbies server only, and the plugin never sees the password. |
| `play` | Starts Echo VR (an installed version, event builds by their id). |
| `game_server` | Proposes the server Echo VR plays on. The launcher asks the player every time. |
| `services: ["server-host"]` | Runs game servers on this PC ([server-host/README.md](server-host/README.md)). Allowed only for a plugin signed by the launcher's makers. Debug builds allow any plugin. |

More limits:

- Copying, opening an address and starting the game work only within a second of a click
  on the plugin's page. The answer to a request sent right after a click counts as that
  click, so Join can ask the server first and then start the game.
- No redirects to other servers and no cookies.
- At most 8 requests out at once. Answers are capped at 4 MB.
- At most 5 notices every 10 seconds.
- At most 32 timers.
- 5 MB of storage, kept in `<plugin>/.data/storage.json`.

## The sandbox

- **Runtime.** wasmtime with the component model. There is no WASI: no files, clock or
  sockets of its own. Everything goes through the imports in
  [`wit/launcher.wit`](../../wit/launcher.wit).
- **Memory.** 64 MB.
- **Time.** `init` gets 2 seconds, every other call 500 ms. When a call runs over, the
  plugin stops and the page says why.
- **Restarts.** **Start again** restarts a stopped plugin, at most 3 times.
- **Thread.** Each plugin runs on a thread of its own and never blocks the launcher.
- **Compiled code.** The launcher keeps it in `<plugin>/.compiled/`, by the component's
  SHA-256 and the launcher's version. Files whose names start with a dot are not part of a
  plugin's signature.

## The interface

The world `plugin` in `wit/launcher.wit` (package `echovr:launcher@0.1.0`).

**What a plugin exports:**

- `init(info)`: once. `info` is `host.launcher-info`.
- `render() -> page`: called when the plugin asked to be drawn (`host.invalidate`) or after
  an event.
- `on-event(event)`.
- `on-timer(id)`.

**What the launcher gives it:**

- **`host`:**
  - `log`, `notify` and `ask` (a dialog; its answer comes back as `event::dialog`).
  - Timers.
  - Storage.
  - `settings` and `set-settings`.
  - `launcher-info`: the installed versions and event builds, the classic lobbies server
    and name, and the server Echo VR plays on. It holds no password and no sign-in.
  - `copy`.
- **`net`:** `fetch` (its answer comes back as `event::net-done`) and `open-url`.
- **`game`:** `play`, `set-server` (its answer comes back as `event::service-done`) and
  `reset-server`.
- **`server-host`:** `call(op, args)` answers at once. `start(op, args)` answers later as
  `event::service-done`. Both take JSON. `console(server)` opens a server's console for a
  `log-view`; its lines never pass through the plugin.

**Events:**

- `clicked` (a table row's button: `<table>/<row>/<button>`), `changed`, `toggled`, `tab`
  and `dialog`.
- `net-done` and `service-done`.
- `settings-changed`.
- `launcher-changed`: what `launcher-info` answers changed.
- `shown` and `hidden`.

**A page** is a flat list of nodes, because WIT has no recursive types. Cards and tabs name
their children by index. Up to two columns: the wide one and the right-hand panel.

The nodes:

- `card`, `text`, `value` (with a Copy button if asked), `chip` and `progress`.
- `field`: a secret field's text stays in the launcher and is never sent to the plugin.
- `choice` and `toggle`.
- `button` and `buttons`: a button with an `icon` is drawn as a small square, and its label
  shows on hover.
- `table`: rows with chips, a detail line and buttons.
- `tabs`.
- `log-view`.
- `form` and `presets`.

## Writing one

The SDK `plugins/sdk` (crate `echovr-plugin`) wraps the bindings:

- the `Plugin` trait and `export_plugin!`;
- `Ui::card(column, title, help, |c| …)` with `c.text`, `c.field`, `c.table`, `c.form`, …;
- helpers for JSON paths, settings and requests.

`plugins/example` is the smallest plugin. It is also the launcher's test fixture.

```sh
rustup target add wasm32-unknown-unknown
cargo install wasm-tools
scripts/build-plugins.sh            # all; or: scripts/build-plugins.sh event-lobbies
```

The script builds each plugin for `wasm32-unknown-unknown` and turns it into a component.
It puts the result beside its `plugin.json` in `docs/plugins/<id>/plugin.wasm`, or for the
example in `src/core/plugin_host/testdata/`.

To try one, copy its folder (`plugin.json`, `plugin.wasm`, `README.md`) into the launcher's
`plugins/` folder, or use a dev folder ([local-plugins.md](local-plugins.md)).
`scripts/sign.py plugin docs/plugins/<id> --zip <id>-<version>.zip` signs a first-party
plugin for the catalogue.

## Snapshots

`ECHOVR_SNAPSHOTS=<dir> ECHOVR_SNAPSHOTS_ONLY=plugin cargo test headless -- --ignored` runs
the plugins' code from `docs/plugins/` with made-up data:

- Event lobbies' requests get made-up answers.
- Server host's servers are made up in a temp folder.

Rebuild the plugins first when their code changed.
